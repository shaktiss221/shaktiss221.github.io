When configuration takes down the internet: Cloudflare 2019 and 2025, and how to ship config safely

A case study of two Cloudflare outages caused by configuration, not code, compared with CrowdStrike 2024 and Google Cloud 2025. Covers what happened on 18 November 2025 (a permission change, a doubled feature file and a panicking proxy) and on 2 July 2019 (a backtracking regex pushed globally), why config and data pipelines bypass the safety nets built for code, and the practices that help (validate generated config like user input, stage every global change, fail safe, kill switches, and keep your incident tooling independent).

Most large outages don’t start with a bad code deploy. Code deploys go through review, tests, canaries and staged rollouts. They start with something that isn’t treated as a deploy: a configuration change, a rules update, a feature file regenerated by a pipeline, a permission tweak in a database. These changes often take effect everywhere within seconds, through fast paths built specifically so that they can. Cloudflare has published two unusually detailed post-mortems of exactly this kind. On 2 July 2019, a single regular expression in a firewall rule pushed to every server at once used up all their CPU for 27 minutes. On 18 November 2025, a database permission change caused an automatically generated “feature file” to double in size, and Cloudflare’s core proxy crashed on it across the network for about three hours, with full recovery taking nearly six. This reading walks through both incidents, compares them with CrowdStrike’s July 2024 crash and Google Cloud’s June 2025 outage, and draws out the engineering practices that make configuration and data changes as safe as code. The earlier reading on progressive delivery covered staged rollouts of code; this one is about everything that ships around them.

1. Why configuration is so dangerous

Configuration is anything that changes a system’s behaviour without changing its binary: feature flags, routing rules, firewall rules, rate limits, allow lists, ML model weights, feature lists, quota policies, DNS records. Several properties make it riskier than code in practice:

  • It’s designed to be fast. The point of a firewall rules pipeline is to block a new attack within seconds everywhere. The point of a feature-flag system is to change behaviour without a deploy. Speed and global reach are the features, and they’re also the blast radius.
  • It skips the code pipeline. Code changes get unit tests, integration tests, canaries and gradual rollout. Config changes often get a schema check, if that.
  • It’s often generated, not written. Many “config files” are produced by other systems: a job queries a database and emits a feature list, a pipeline compiles rules, a service publishes a policy. A change upstream (to the data, the query, or the permissions behind it) changes the output with nobody reviewing the output itself.
  • It’s trusted. Code that parses user input is defensive. Code that loads the company’s own config files usually isn’t, because “we generated it, so it’s valid”.
  • It’s shared. One config file is read by every server, so one bad value hits everything at once.

Google’s SRE writing and Facebook’s paper on its configuration system (Tang et al., “Holistic Configuration Management at Facebook”, SOSP 2015) both make the same point: config changes are a major source of production incidents, and they deserve the same rigour as code, including review, automated validation, canarying and gradual rollout.

2. Cloudflare, 2 July 2019: one regex, every CPU

What happened

Cloudflare’s Web Application Firewall (WAF) inspects HTTP requests using managed rules, many of them regular expressions, and the WAF rules pipeline was designed to push new rules to the whole network quickly so that emerging attacks could be blocked fast.

At 13:42 UTC an engineer deployed an update to WAF rules. One new rule contained a regular expression that, simplified, looked like .*(?:.*=.*). Two .* patterns in sequence force a backtracking regex engine to try a huge number of ways of splitting the input when no match is found. Cloudflare’s write-up shows how fast the step count grows with input length: thousands of steps for a 20-character string, and far more for realistic request sizes.

The rule was meant to run in “simulate” (log-only) mode, but it was still evaluated against live traffic, so its cost was paid on every request. Because the WAF deployment process allowed global pushes, the rule reached every server at once. CPU usage on every core handling HTTP and HTTPS traffic spiked to nearly 100%, and Cloudflare’s proxies started returning 502 errors across the network.

Cloudflare’s engineers used a global kill switch to disable the WAF at 14:07; traffic and CPU were back to normal by 14:09. The outage lasted 27 minutes.

What made it worse

The post-mortem was frank about contributing factors:

  • A CPU protection had been removed. The WAF had previously had a safeguard against excessive regex CPU use; it had been removed weeks earlier during a refactor and not replaced.
  • The regex engine (a backtracking engine) didn’t guarantee linear-time matching.
  • Global deployment was allowed for WAF rules, by design, with no staged rollout.
  • Incident tooling depended on the failing system. Access to internal dashboards and tools went through Cloudflare’s own network, which made it harder to respond.

Remediation

Cloudflare’s listed fixes became a template for config safety:

  • Re-introduce CPU protection and review all of the thousands of existing managed WAF rules for backtracking risk.
  • Add performance profiling of rules to the test suite.
  • Switch to a regex engine with linear-time guarantees (Rust’s regex crate or RE2), which don’t backtrack and so can’t blow up this way.
  • Change the procedure so WAF rule changes roll out in stages, like code, with global emergency pushes reserved for active attacks.
  • Make sure dashboards and APIs can be reached even if the edge is down.

The regex engine change is the deepest fix: it removed an entire class of failure rather than catching one instance of it.

3. Cloudflare, 18 November 2025: a doubled feature file

What happened

Cloudflare’s Bot Management system scores each request on how likely it is to come from a bot, using a machine-learning model. The model’s inputs (“features”) are described in a feature file that’s regenerated every few minutes by a query against Cloudflare’s ClickHouse analytics database and pushed to every machine in the network, so the model can adapt quickly to new bot behaviour.

The chain of events, from Cloudflare’s post-mortem:

  1. A database permission change. At 11:05 UTC, a change to ClickHouse permissions was deployed as part of an effort to make access more explicit. After the change, users could see metadata for tables in an additional underlying database (r0) that had previously been hidden from them.
  2. The query returned duplicates. The query that builds the feature file read column metadata without filtering by database name. With the extra visibility, it returned each feature’s columns twice.
  3. The feature file doubled in size. The file now listed far more features than usual.
  4. It was pushed everywhere. The new file propagated to every machine as designed.
  5. The proxy panicked. Cloudflare’s core proxy preallocates memory for Bot Management features and enforces a limit of 200 features (normal usage was around 60). The doubled file exceeded the limit. In the newer Rust-based proxy (FL2), that error reached an unwrap() on an Err value, which panics, so requests that used Bot Management failed with HTTP 5xx errors. Customers on the older proxy (FL) didn’t get errors, but every request got a bot score of zero, which broke rules that blocked bots.

Network-wide failures began at about 11:20 UTC. Core traffic was largely flowing again by 14:30, and everything was fully restored by 17:06.

Why it was hard to diagnose

Two things misled the responders:

  • The errors came and went. The ClickHouse cluster was being updated node by node, so the query that generated the feature file sometimes ran on an updated node (producing a bad file) and sometimes on an old one (producing a good file). Every five minutes the network got either a good or a bad file, so the system kept recovering and failing again. That pattern looks much more like an attack than like a bad deploy.
  • Cloudflare’s status page went down at the same time. It’s hosted independently of Cloudflare’s infrastructure, and its failure was a coincidence, but together with the fluctuating errors (and a run of record-setting DDoS attacks in the preceding weeks), it led the team to suspect a massive attack at first.

Once the feature file was identified, the team stopped the generation and propagation of new files, manually inserted a known-good file into the distribution queue, and restarted the proxy fleet. Many downstream services (Workers KV, Access, the dashboard’s login with Turnstile) depended on the core proxy and recovered in turn.

Remediation

Cloudflare listed these themes:

  • Harden ingestion of Cloudflare-generated configuration files the same way as user-generated input. In other words, stop trusting internal data just because it’s internal.
  • Add more global kill switches for features, so a misbehaving module can be turned off everywhere quickly.
  • Stop core dumps and error reporting from overwhelming system resources, which had added to the load during the incident.
  • Review failure modes for error conditions across all core proxy modules.

4. The same pattern elsewhere

CrowdStrike, July 2024

CrowdStrike’s Falcon sensor runs inside the Windows kernel and receives Rapid Response Content, configuration-like updates that tell the sensor what behaviours to detect, separately from sensor code releases and much more frequently. According to CrowdStrike’s root cause analysis, a template type added earlier in 2024 defined 21 input fields, but the integration code that invoked it supplied only 20 values. On 19 July 2024, two new content instances used the 21st field. The sensor’s content interpreter read beyond the end of its input array, and because it runs in the kernel, the out-of-bounds read crashed Windows. Microsoft estimated that about 8.5 million Windows devices were affected, less than 1% of all Windows machines but concentrated in airlines, hospitals, banks and broadcasters. Many machines needed manual intervention to recover.

The parallels with Cloudflare 2025 are striking: a content/config channel designed for fast global delivery, a mismatch between what the data contained and what the consuming code expected (21 vs 20 fields; more than 200 features), validation that trusted the data, and a crash rather than a graceful fallback. The progressive delivery reading covered CrowdStrike’s subsequent move to staged content deployment.

Google Cloud, June 2025

On 12 June 2025, a large Google Cloud outage affected many products for several hours. Google’s incident report described a new feature in Service Control, the system that checks API requests against quota and policy, that had been rolled out region by region but whose new code path wasn’t protected by a feature flag. When a policy change containing unintended blank fields was written to the globally replicated policy data store, it reached every region within seconds; the new code path hit a null pointer on the blank fields and crashed in a loop everywhere. Recovery in the largest region took longer because restarting tasks overloaded the infrastructure they depended on.

Again: code rolled out carefully, but data replicated globally in seconds and exercised an untested path, with no flag to turn it off and no graceful handling of unexpected input.

5. The common anatomy

Put side by side, these incidents share a structure:

Trigger Fast global path Unvalidated assumption Failure mode
Cloudflare 2019 new WAF rule WAF rules pushed to all servers at once regexes are cheap CPU exhaustion
CrowdStrike 2024 new detection content Rapid Response Content to all sensors input has the expected field count kernel crash
Google Cloud 2025 policy data with blank fields globally replicated policy store fields are populated null-pointer crash loop
Cloudflare 2025 DB permission change feature file regenerated and pushed every few minutes feature count stays under 200 proxy panic

Four lessons fall out.

  1. The dangerous change wasn’t recognised as a deploy. A rule update, a content file, a policy row, a permissions change: none went through the staged rollout that code would have.
  2. Global propagation was fast by design, so there was no window for canaries to catch the problem.
  3. The consuming code trusted the data. A limit, a field count or a non-null assumption was enforced by crashing.
  4. Recovery needed a separate lever (a kill switch, a known-good file, a manual fix), and how quickly it could be pulled determined the outage length.

6. Practices that help

Treat config and data as deploys

  • Version and review configuration like code. Store it in a repository or a system with history, diffs and approvals.
  • Stage every change, including generated ones: a canary set of machines, then a region, then the world, with automated health checks between stages. Emergency fast paths should exist but require an explicit, logged decision. After 2019, Cloudflare reserved global WAF pushes for active attacks.
  • Diff generated outputs. When a pipeline regenerates a file, compare the new output with the last one: size, number of entries, distribution of values. A feature file that doubles in size, or a rule set whose evaluation cost jumps, should stop the pipeline and page someone rather than ship. Facebook’s Configerator, for example, runs validators and canary tests on config changes before they’re distributed.
  • Know your config’s upstream dependencies. The Cloudflare 2025 trigger was a permission change in a database that a config generator read from. Map which data sources feed generated configs, and treat changes to those sources as changes to the configs.

Make consumers defensive

  • Validate internal input like external input. Check schema, sizes, counts and ranges on load. Cloudflare’s main remediation is exactly this.
  • Fail safe, not fatal. If a new config is invalid, keep running with the last known good version and alert, instead of crashing. Most systems that load config periodically can do this, and it turns “global outage” into “stale config for a while”. The equivalent in code is not using unwrap(), assert or unchecked array access on paths fed by external data.
  • Remove whole classes of failure. Linear-time regex engines, memory-safe parsers, bounded interpreters, and strict schemas with generated parsers eliminate categories of bug instead of catching instances.
  • Bound resource use. Per-request CPU limits, timeouts on rule evaluation, and size limits enforced with clear errors (not panics) contain the damage of a bad rule.

Prepare the escape hatches

  • Kill switches for each major feature or module, reachable globally within seconds, tested regularly. Both Cloudflare incidents were ended by switching something off.
  • Pinning and rollback for generated config: the ability to freeze the pipeline and push a known-good file. In 2025 this was the critical recovery step.
  • Feature flags around new code paths that consume new kinds of data, as Google’s report emphasised, so a crash can be avoided by turning the path off.
  • Independent incident tooling. Dashboards, status pages, chat, paging and access to production must not depend on the system that’s failing. Cloudflare’s 2019 incident was slowed by tools that went through its own edge.

Learn from the near misses

  • Watch for flapping. An error rate that oscillates on a regular cycle points to something periodic: a cron job, a pipeline cadence, a rolling update. In 2025 the five-minute cycle was the clue that the problem was the feature file.
  • Write down “impossible” states. The 200-feature limit was reasonable, but nothing monitored how close the system was to it. Alert on approaching limits, not just on crossing them.

7. How this connects to resilience patterns

The resilience reading covered timeouts, retries and circuit breakers for calls between services. Config safety is the same philosophy applied to a different input:

  • Bulkheads and cells limit blast radius. If configuration is rolled out cell by cell, a bad file breaks one cell, not the world.
  • Graceful degradation (serving with a stale config, or with a feature disabled) beats failing closed for most features. Whether a security feature should fail open or closed is a deliberate product decision, worth making in advance rather than during an incident.
  • Metastable failures: restarting thousands of crashed processes at once can overload shared dependencies, which happened in the Google Cloud recovery. Staggered restarts and backoff apply to recovery too.

Key takeaways

  • Configuration, rules, content and generated data are deploys, and they cause many of the largest outages precisely because they skip the safeguards built for code.
  • Cloudflare 2019: a backtracking regex in a WAF rule, pushed globally at once, saturated CPU network-wide for 27 minutes. Fixes: linear-time regex engines, rule profiling, staged rollouts.
  • Cloudflare 2025: a ClickHouse permission change made a feature-file query return duplicates; the file exceeded the proxy’s 200-feature limit and the proxy panicked. Errors began around 11:20 UTC, with full recovery at 17:06. Fixes: treat internal config like user input, more kill switches, review failure modes.
  • CrowdStrike 2024 (21 vs 20 fields, about 8.5 million devices) and Google Cloud 2025 (blank policy fields, no feature flag) follow the same pattern.
  • Practices that help: stage all global changes, diff generated outputs, validate on load, fall back to last known good, build kill switches, flag new code paths, and keep incident tooling independent.

Discussion questions

  1. List the ways production behaviour can change in your systems without a code deploy. Which of them roll out in stages, and which reach everything at once?
  2. Do you have any generated config files (feature lists, allow lists, routing tables)? What would happen if one doubled in size or came out empty tomorrow?
  3. Your service loads a config file that fails validation. Should it crash, keep the old config, or run with defaults? Does the answer differ for a security feature?
  4. Cloudflare’s errors flapped every five minutes. What other periodic signals in your systems could mislead an incident response, and how would you spot them?
  5. Which of your incident tools (dashboards, status page, chat, deploy system) would still work if your main production platform were down?
  6. Where in your code does an “impossible” condition from data cause a panic, an assert failure or an unchecked access? How would you find those places?
