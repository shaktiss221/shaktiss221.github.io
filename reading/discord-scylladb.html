Discord's messages: Cassandra to ScyllaDB

How Discord moved trillions of messages to ScyllaDB, and the data-services layer that stopped hot channels hurting everyone else.

In 2022 Discord moved trillions of messages from a 177-node Cassandra cluster to 72 ScyllaDB nodes, cut p99 read latency from as high as 125 ms to about 15 ms, and copied the data in 9 days. The database swap gets the headlines, but the bigger lesson is the layer Discord put in front of it, which stopped hot channels from hurting everyone else. This piece follows Discord’s two engineering blog posts, from 2017 and 2023, and pulls out what applies to other systems. Reading time is about 30 minutes.

1. 2015 to 2017: from MongoDB to Cassandra

The starting point

Discord launched in 2015 with messages in a single MongoDB replica set, with a compound index on channel ID and creation time. That was a deliberate choice to move fast. By November 2015 it held around 100 million messages, and the data and indexes no longer fit in RAM, so latencies became unpredictable. The team went looking for a database that would scale horizontally and stay boring to operate.

Their requirements, from the 2017 post, are a good template for any database choice:

  • Linear scalability: add nodes, get capacity, no manual resharding.
  • Automatic failover: the database heals itself at night without an on-call engineer.
  • Low maintenance once set up.
  • Proven at scale: not a database they would be the first to push this hard.
  • Predictable performance: alert if the API’s p95 goes over 80 ms, and avoid caching messages in a separate layer.
  • Not a blob store: they write thousands of messages per second, so read-modify-write of blobs was out.
  • Open source.

The workload shape mattered as much. Reads are extremely random, because users jump to old messages, search results and mentions across many channels, while writes are mostly appends. The read-to-write ratio was roughly 50/50. Cassandra fit: a Dynamo-style ring with tunable consistency, fast appends through its log-structured storage, and big users (Apple, Netflix) at much larger scale.

The data model

Cassandra is a wide-column store: data is grouped into partitions by a partition key, and rows inside a partition are sorted by clustering columns. A query that names one partition and a slice of clustering keys is fast; anything else is expensive. So the schema had to match the dominant query: fetch the most recent messages in a channel, or the messages around a given point.

The obvious design, partition by channel_id and cluster by message ID, fails because a busy channel would grow one partition without bound, and Cassandra partitions need to stay well under about 100 MB for good performance. Discord added a time bucket to the partition key:

CREATE TABLE messages (
  channel_id bigint,
  bucket     int,
  message_id bigint,
  author_id  bigint,
  content    text,
  PRIMARY KEY ((channel_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);

The bucket is a static window of time, 10 days, derived from the message ID itself. Even the busiest channels would then stay under the partition size target. To read recent history, the client queries the current bucket and walks backwards bucket by bucket until it has enough messages. For quiet channels this can mean probing many empty buckets, which is acceptable because quiet channels are cheap.

Snowflake IDs

Discord uses Snowflake IDs, the scheme Twitter published in 2010: a 64-bit integer whose top 42 bits are a millisecond timestamp (counted from Discord’s own epoch, the first second of 2015), followed by worker and process IDs and a per-process sequence number. That gives three properties the design relies on:

  • IDs are unique without coordination, generated by any API server.
  • IDs sort by time, so message_id is both the primary key and the chronological order.
  • The timestamp is embedded, so the bucket can be computed from the ID alone: bucket = (message_id >> 22) / ten_days_in_ms.

Surprises in year one

The 2017 post is candid about what bit them:

  • Eventual consistency and upserts. Cassandra writes are upserts. If a user edited a message at the same moment another user deleted it, the edit could write a row containing only the edited columns, leaving a message with no author or content. Their fix was to detect such corrupt rows on read and delete them, and to only write the columns being changed.
  • Tombstones. A delete in Cassandra writes a tombstone marker, kept for gc_grace_seconds (10 days by default) so deletions propagate to replicas that were down. One public server deleted millions of messages, leaving almost nothing visible. Reading that channel meant scanning millions of tombstones to find a handful of live rows, which caused long garbage-collection pauses on the JVM. They reduced the grace period to 2 days, matched to their nightly repair schedule, and avoided writing null values, since nulls are tombstones too.

The cluster launched with 12 nodes and replication factor 3. The post ended optimistically, noting that the next step might be ScyllaDB, “a Cassandra-compatible database written in C++”. Five years later, that is what happened.

2. 2017 to 2022: what broke at trillions of messages

By early 2022 the cassandra-messages cluster had grown to 177 nodes holding trillions of messages. The 2023 post describes it as “high-toil”: on-call engineers were frequently paged, latency was unpredictable, and maintenance operations had become too expensive to run routinely. None of the problems were exotic. They were the normal failure modes of a log-structured, JVM-based database meeting a skewed workload.

Hot partitions

Discord’s traffic is extremely skewed. A large server with hundreds of thousands of members, during a game launch or a big announcement, can generate a burst of reads and writes against a single channel, and therefore against one partition, which lives on exactly three nodes (replication factor 3).

What made this painful was the blast radius. When one of those nodes slowed down under the hot partition, every query it served slowed down, including queries for unrelated quiet channels whose data happened to live on it. Because Discord read and wrote at QUORUM consistency, a request needs two of three replicas to answer, so one slow node in a replica set dragged out requests touching that set. Clients and the API then retried or piled up concurrent requests, adding load to the slowest node. A single popular channel could degrade latency across a large part of the cluster.

Reads are expensive in an LSM tree

Cassandra stores data in a log-structured merge tree (LSM):

  1. Writes go to a commit log and an in-memory memtable. That makes writes cheap: an append and a memory insert.
  2. When the memtable fills, it’s flushed to disk as an immutable SSTable.
  3. Over time a partition’s rows are spread across many SSTables, so a read may have to check the memtable and several SSTables (Bloom filters help skip ones that definitely don’t contain the key) and merge the results.
  4. Background compaction merges SSTables to keep the count per read low and to purge tombstones and overwritten values.

This is why the 2023 post notes that in Cassandra reads are more expensive than writes. A workload with 50/50 reads and writes and highly random read patterns, like Discord’s, leans on the expensive side.

Compaction debt

Compaction is the tax that keeps reads fast, and it competes with foreground traffic for disk and CPU. When nodes were busy, compaction fell behind. More SSTables per partition meant slower reads, slower reads meant more concurrent requests in flight, and that meant even less capacity for compaction: a feedback loop.

The operational workaround Discord describes is telling. Engineers would perform what they called a “gossip dance”: take a struggling node out of rotation so it received no client traffic, let it compact in peace, then put it back. Doing that by hand across a 177-node cluster is exactly the kind of toil that burns out an on-call rotation.

Garbage collection pauses

Cassandra runs on the JVM. Large heaps, high allocation rates from reads, and tombstone-heavy partitions produce GC pauses that stall a node for hundreds of milliseconds or more. A paused node looks, to its peers and to clients, like a slow or briefly dead node, which triggers the same quorum-latency and retry effects as a hot partition. Discord had spent significant effort on JVM and GC tuning, and still saw latency spikes they attributed to GC.

Why this combination is hard

Each problem alone is manageable. Together they compound:

Trigger Immediate effect Knock-on effect
Hot partition on 3 nodes Those nodes saturate Unrelated queries on the same nodes slow down
Slow node in a quorum p99 latency rises for its replica sets Retries and queued requests add more load
Compaction falls behind More SSTables per read Reads get slower, leaving less headroom for compaction
GC pause Node stalls Looks like a failure to clients and peers

At this point Discord had a choice: keep tuning Cassandra, or change something structural. They changed two things: the database, and, more importantly, how traffic reached it.

Why ScyllaDB

Discord had already moved other clusters to ScyllaDB and had good experience with it. ScyllaDB is a reimplementation of Cassandra’s data model and query protocol (CQL) in C++, built on the Seastar framework:

  • No garbage collector. Memory is managed manually, so there are no stop-the-world pauses.
  • Shard-per-core architecture. Each CPU core owns a slice of the node’s data and its own memory, and cores communicate by message passing, not locks. A hot partition saturates one core’s shard rather than the whole node, and there’s no lock contention.
  • Its own I/O and CPU schedulers that prioritise foreground queries over background work like compaction, adjusting compaction’s share automatically based on backlog. That targets the exact compaction-debt loop above.
  • Drop-in compatibility: the same schema, CQL drivers and data model, so the application code barely changed.

It wasn’t free. Discord’s messages workload relied heavily on reverse queries (reading a partition in the opposite order to its clustering order, to page through history), which ScyllaDB at the time didn’t perform well enough for them. The ScyllaDB team prioritised improvements to reverse-query performance before the migration could go ahead, a reminder that “compatible” doesn’t mean “performs the same on your access pattern”.

3. The new design: data services in front of ScyllaDB

Swapping Cassandra for ScyllaDB would have removed GC pauses and eased compaction, but it wouldn’t fix hot partitions: a channel with 100,000 people reading at once would still send 100,000 reads to three replicas. Discord’s answer was an intermediary layer they call data services.

What a data service is

A data service is a small Rust service that sits between Discord’s API monolith and the database. It exposes one gRPC endpoint per database query (for example, “get messages in channel X before message Y”), and contains no business logic. Its job is to protect the database.

The 2023 post highlights two features.

Routing sends every request for a channel to the same data service instance, and that instance collapses concurrent identical reads into one query.

Feature 1: request coalescing

When several users ask for the same rows at the same moment, which is exactly what happens when an @everyone ping goes out in a big server, the data service runs the database query once:

  1. The first request for a given key spawns a worker task that runs the query.
  2. Requests for the same key that arrive while it’s in flight don’t issue their own query. They subscribe to the existing task.
  3. When the result returns, every subscriber gets it.

This pattern is often called single-flight (after Go’s golang.org/x/sync/singleflight package). It’s not a cache: nothing is stored after the query completes, so there’s no invalidation problem and no stale data beyond the duration of one query. It only removes duplicate work that overlaps in time, which is precisely the shape of a hot-channel burst. Rust’s async runtime (Tokio) made the many-subscribers-per-task model cheap and safe to write.

Feature 2: routing by channel

Coalescing only works if concurrent requests for the same channel reach the same data service instance. If 100 instances each received one request for channel 123, each would run its own query. So Discord routes requests upstream of the data services by consistent hashing on the channel ID (the subject of yesterday’s piece), so all traffic for a channel lands on one instance. Requests for different channels spread evenly across the fleet.

That’s a neat combination: consistent hashing makes coalescing effective, and coalescing caps the database load from any single hot key at roughly one query per key per round trip, no matter how many clients ask.

Why put this in a separate layer?

Discord could have added coalescing inside the API monolith. A separate service has advantages worth copying:

  • Language fit. Rust gave predictable latency (no GC, the same reason they wanted ScyllaDB), fearless concurrency for the subscriber model, and good performance per core.
  • Independent deploys and scaling. The data layer can scale with database traffic, not with API traffic.
  • One choke point for database protections. Concurrency limits, timeouts, query shapes and metrics all live in one place, rather than in every caller.
  • A seam for migrations. Because all database access goes through data services, changing the database underneath becomes a change in one service, not hundreds of call sites. This turned out to matter a great deal for the migration in the next section.

Storage underneath

The database nodes themselves also changed. In a separate 2022 post, Discord described a “superdisk” setup on Google Cloud: a software RAID that mirrors local NVMe SSDs, for fast reads, with a persistent network disk for durability, configured so reads are served from the local SSDs and writes go to both. That gave them local-disk read latency without losing data when a VM’s local SSDs disappear. ScyllaDB nodes in the new cluster each held around 9 TB, more than double the Cassandra nodes’ average, which is part of why far fewer nodes were needed.

4. The migration, the results and the lessons

The plan they abandoned

The original plan was the textbook one:

  1. Stand up the new ScyllaDB cluster.
  2. Start dual-writing new messages to both Cassandra and ScyllaDB, using a cutover point in time.
  3. Backfill historical data with ScyllaDB’s Spark-based migrator.
  4. Validate, switch reads, decommission Cassandra.

The estimate for the Spark migration of trillions of messages was about three months. For a team whose main motivation was reducing on-call pain, three months of nursing the old cluster while also running a giant batch job was unattractive.

The migrator they wrote instead

Discord already had Rust data-service code that read from and wrote to Cassandra-compatible databases efficiently. So they extended it into a purpose-built migrator:

  • It read token ranges from Cassandra, so work could be split into independent chunks.
  • It tracked progress per range in a local SQLite database as a checkpoint, so it could stop and resume without redoing work.
  • It wrote into ScyllaDB as fast as the clusters allowed, reaching about 3.2 million messages per second.

The new estimate was 9 days. And that’s roughly how it went, with one snag at the very end: progress stalled at about 99.9999%. The stuck token ranges contained enormous runs of tombstones that had never been compacted away in Cassandra, so reading through them was extremely slow. Compacting those ranges in Cassandra cleared the blockage, and the migration completed within seconds afterwards. Tombstones, the trouble from 2017, made a final appearance.

Validation and cutover

Before switching reads, they sent a small percentage of reads to both databases and compared results automatically, a technique often called shadow reads. Once mismatches were explained or fixed and the comparison stayed clean, reads moved to ScyllaDB. The cutover happened in May 2022, and the Cassandra cluster was decommissioned afterwards. Because all access went through data services, cutover was a change in one layer rather than across the codebase.

Results

Measure Cassandra (before) ScyllaDB + data services (after)
Nodes 177 72
Disk per node about 4 TB average about 9 TB
p99 read latency (historical messages) 40 to 125 ms about 15 ms
p99 insert latency 5 to 70 ms steady about 5 ms

The post also points to an unplanned stress test: the 2022 FIFA World Cup final in December, where Argentina beat France on penalties. Discord’s message graphs show distinct spikes for each goal and for the shootout, and the new stack absorbed them without trouble. Fewer nodes, much tighter tail latency, and far less weekend firefighting.

Lessons that generalise

1. Protect the database with a layer you control. The data-services layer did as much for Discord as the database change. Request coalescing (single-flight), per-key routing and concurrency limits are applicable to any database, including Postgres or DynamoDB. If hot keys hurt you today, a single-flight layer in front of the database is often the cheapest big win.

2. Pick the data model for the access pattern, then size the partitions. The (channel_id, bucket) key with 10-day buckets aged well from billions to trillions of messages. Bounding partition size with a time bucket is a reusable trick for any wide-column or key-value store.

3. Prefer predictable latency over peak throughput. Most of Discord’s pain was the tail: GC pauses, compaction stalls, one slow replica in a quorum. Both of their main choices (ScyllaDB’s no-GC shard-per-core design, and Rust for data services) target tail latency rather than average throughput.

4. Understand the LSM trade-offs you’re buying. Cheap writes, more expensive reads, compaction as an ongoing tax, and tombstones that linger. Those trade-offs are shared by Cassandra, ScyllaDB, RocksDB-based systems and HBase. Plan deletes carefully, and watch compaction backlog as a first-class metric.

5. Migrations go faster when you build the tool that fits. A resumable, range-based copier with checkpoints and shadow-read validation turned a three-month project into nine days. The general recipe (split the keyspace, checkpoint progress, verify with dual reads, cut over behind an abstraction) applies to most large data migrations.

6. “Compatible” isn’t “equivalent”. Even a drop-in replacement needed upstream work on reverse queries before it could carry this workload. Test the new system against your real query mix, not a benchmark.

A note on what we can’t see

Engineering blog posts are written after the fact, and they emphasise what worked. The posts don’t detail costs, licensing, or how much of the latency gain came from the database versus the data services versus the new disks. Treat the numbers as directionally reliable and Discord-specific, and the patterns as the transferable part.

Discussion questions

  1. Discord’s bucket is a fixed 10 days for every channel. What are the costs for very quiet and very busy channels, and how would you design adaptive bucketing? What would it complicate?
  2. Request coalescing only helps when identical requests overlap in time. Which of your own hot paths have that shape, and which would need a real cache instead?
  3. Routing by consistent hash on channel_id sends a viral channel’s traffic to one data-service instance. When does that become a problem, and what would you do about it?
  4. If Discord had kept Cassandra but added the data-services layer, how much of the improvement do you think they would have got? Which problems would remain?
  5. Design a migration for a 50 TB table in your stack using the same recipe: range-split copy, checkpoints, shadow reads, cutover behind an abstraction. Where are the risky steps?
  6. The 2017 post chose Cassandra partly because it was “proven at scale”; the 2023 post moved away after five years. What signals would tell you, early, that a database choice is reaching its limits?
